## Spike: can mlx-swift's fatal error handler be replaced? — YES

Evidence, from mlx-swift 0.31.6 `Source/MLX/ErrorHandler.swift` (read at
`~/Library/Developer/Xcode/DerivedData/PyMOLViewer-*/SourcePackages/checkouts/`):

- `setErrorHandler` is `@available(*, deprecated, message: "please use
  withErrorHandler() or withError()")`.
- `public func withError<R>(_ body: () throws -> R) throws -> R` converts MLX errors
  into Swift `throws` on block exit.
- `ErrorHandler.dispatch(_:)` calls `fatalError(message)` ONLY when there is neither
  a task-local nor a global handler. With a handler installed it calls the handler
  and RETURNS — the handler need not terminate.

Action taken: added `MPNNRuntime.withMLXErrorsAsThrows(_:)` wrapping `withError`, and
routed all three MPNNKit call sites through it. MLX-reported errors now propagate as
Swift errors through the continuation into `DesignController`'s do/catch, which sets
`errorText`, which Task 1's banner displays.

CORRECTION THIS FORCES: the Phase 2d spec section 10 states that mlx-swift's handler
"prints then exits, so DesignController's do/catch ... can never observe an
allocation failure". That is FALSE for 0.31.6. The doc comments in both MPNNRuntime
and DesignSizeGuard now state the accurate distinction:
  - MLX-REPORTED errors are catchable via `withError`.
  - A JETSAM SIGKILL is an OS kill, not an MLX error, and cannot be caught by any
    handler — which is why DesignSizeGuard must stay PREVENTIVE.
The spec itself is corrected in Task 14, which already edits that document.

## Task-8 review-pass findings (applied 2026-07-26)

Commit: 54291fc90

### Finding 1 — setenv order bug (latent crash in simulator) — FIXED
`setenv("MLX_METAL_GPU_ARCH"…)` ran AFTER `MLX.GPU.set(cacheLimit:)`. Setting
the cache limit lazily constructs MLX's `MetalAllocator`, whose constructor
reads `MLX_METAL_GPU_ARCH` into a function-local static (first call wins,
forever). With the old order the env var was still unset when the static was
latched, so the simulator fallback silently did nothing — first simulator
inference would have ABORT'd.
Fix: `#if targetEnvironment(simulator)` block moved above the cache-limit line;
explanatory comment added.

### Finding 2 — model loader not wrapped — FIXED
`MPNNModel(packDirectory: url)` now wrapped in `withMLXErrorsAsThrows`; a
corrupt `.mpnnpack` now surfaces as the Design error banner instead of a crash.
`withMLXErrorsAsThrows` doc comment updated to say "every call that can touch
MLX — including model construction".

### Finding 3 — deprecated `GPU.set(cacheLimit:)` — FIXED
Replaced with `MLX.Memory.cacheLimit = cacheLimitBytes`.
`MLX.Memory.cacheLimit` confirmed as a read-write property in mlx-swift 0.31.6
`Source/MLX/Memory.swift` line 251. Deprecation warning is gone from the build.

### Finding 4 — non-fail-fast semantics undocumented — FIXED
`withMLXErrorsAsThrows` doc comment now describes the non-fail-fast behaviour:
`withError` records the first error at dispatch time but throws only at block
exit; intermediate arrays may produce additional errors but no wrong result
escapes because `check()` always throws before the block value is returned.

### Finding 5 — `canLoadModel()` bypassed configureOnce + error wrapper — FIXED
`MPNNGate.canLoadModel()` deleted (zero callers confirmed). `packURL` retained
(used by `loadedMPNNModel()` and inference tests).

### Finding 6 — no test for MPNNRuntime — FIXED
Two tests added to the existing `DesignIOSPortTests.swift` (no new file):
- `testCacheLimitConstantIs96MB`: asserts the constant equals 96 * 1024 * 1024
- `testConfigureOnceInstallsCacheLimit`: calls `configureOnce()` and reads
  `activeCacheLimitBytes` (a new thin accessor on `MPNNRuntime` that returns
  `MLX.Memory.cacheLimit`) — asserts the live limit matches `cacheLimitBytes`

The test target does not import MLX; the accessor keeps `MPNNRuntime` as the
only importer.
